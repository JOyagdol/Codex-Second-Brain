# 기존 문서·구현 대응과 최종 검토

## 근거 수집

원본의 파일명·버전·작성 시점과 실제 제출 여부를 구분하라. 코드 확인 시 저장소·브랜치·커밋 또는 파일 해시와 읽은 범위를 기록하라. 실행하지 않았다면 정적 검토라고 밝혀라. README 설명보다 실제 조건 분기·계산식·호출 설정을 확인하되, 코드 자체를 항상 의도된 발명의 정답으로 간주하지 마라. 버그 가능성은 사실 설명과 개선 제안을 분리하라.

입력 스키마, 호출 경로, 후보 선정, 필터, 임계값, 예외, 결과 유형·방향, 저장 속성을 추적하라. 부분 파일 검토를 저장소 전체 최신 검증으로 표현하지 마라. 프로젝트 지침과 실행 허용 범위를 따르며 신고서 작성 때문에 코드를 임의로 수정하지 마라.

## 대응표

| 구성·절차 | 기존 문서 근거 | 현재 구현·자료 근거 | 분류 | 신고서 처리 | 확인할 사항 |
|---|---|---|---|---|---|
| 실제 항목 | 문단·쪽·도면 | 파일·함수·버전 또는 실험 자료 | A/B/C | 유지·정정·구체화·변형예·제외 | 구체적 질문 |

- A: 기존 자료에서 해당 개념을 확인함.
- B: 기존 설명과 관련되지만 세부 처리의 기재 근거를 확인해야 함.
- C: 제공된 기존 자료에서 해당 추가 내용의 근거를 확인하지 못함.

이 표는 기술 자료 정리이다. A를 출원 당시 충분한 기재 또는 우선일 인정으로, C를 법률상 신규사항 확정으로 사용하지 마라. 개념 기재와 구체 알고리즘 기재를 구별하라. 기존 자료가 없으면 A/B/C를 만들지 말고 새 발명의 구성–근거–미확인 표로 바꾸라.

## 필수 구성 변경표

| 이전 구성 | 현재 처리 | 이유 | 발명의 중심에 미치는 영향 |
|---|---|---|---|
| 실제 항목 | 유지/선택화/변형예/삭제/정의 수정 | 자료와 기술적 이유 | 해결 과제·대상·효과 변화 |

사용자가 승인한 범위 변경을 되돌리지 마라. 표준 형식, 데이터베이스, 개별 수치처럼 교체 가능한 구현 선택을 핵심으로 고정할 이유가 있는지 검토하라. 반대로 발명의 핵심 처리까지 모두 선택화하지 마라. 특정 구성의 제외는 더 넓은 권리 확보를 보장하지 않는다.

## 완성도 판정

결과를 세 부류로 구별하라.
1. 지금 고칠 오류: 본문·그림 불일치, 정의 혼용, 불가능한 예제, 수식 오류, 구현 과장.
2. 선택적 보강: 실제 실행 사례, 추가 비교, 변형예, 더 읽기 쉬운 그림.
3. 외부 확인: 실제 출원본, 관련 과제·공개 이력, 원기재와 후속 내용의 관계, 선행기술 대비 권리 구성.

첫째는 가능한 범위에서 고쳐라. 둘째를 필수인 것처럼 만들어 완료를 늦추지 마라. 셋째는 확인할 자료·질문을 구체화하라. 선행기술 조사가 실제로 이루어졌는지, 특허사무소 의뢰 범위에 포함되는지 확인되지 않았다면 자동 완료로 간주하지 마라.

## 후속 청구범위 검토

요청받은 경우 구성요소–본문 근거–기존 자료 근거–도면 대응표를 만들라. 독립항과 종속항의 관계, 선행 표현, 선택 조건, 장치·방법 간 처리 일치를 확인하라. 프로그램이나 기록매체 표현은 해당 기술과 관할 검토에 맞춰 후보로 작성하라. 신고서 작성 단계에서 모든 발명에 동일한 청구항 개수·유형을 강제하지 마라.

법률·절차에 대한 판단을 제공할 때 현재 관할의 공식 자료를 조회하라. 특허사무소 전달 문구는 ‘확인 필요’로만 끝내지 말고 예를 들어 ‘이 처리의 기존 제출본 근거와 이번 절차에서의 반영 가능성을 확인해 달라’처럼 요청을 특정하라. 사용자 승인 없이 외부에 발송하지 마라.
