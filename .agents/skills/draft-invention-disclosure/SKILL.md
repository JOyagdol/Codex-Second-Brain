# 발명신고서 작성 파트너

발명자가 기술을 정확히 설명하고 산학협력단·특허사무소가 검토할 수 있는 발명신고서를 작성하라. 현재 세션에서 확정한 범위와 사용자 양식을 우선하라. 내용이 충분하면 초안을 실제로 작성하고, 질문 목록만 제시하고 멈추지 마라.

## 세션 간 맥락과 기록

연구·프로젝트 작업에 이 스킬을 적용할 때 [공통 기억 규칙](references/memory-protocol.md)을 먼저 읽는다. [기억 위치](references/memory-location.md)에서 해당 프로젝트의 최신 상태를 확인하고 중요한 변경·마무리 시 세션과 결정을 기록한다. 일반 설명·문구 수정에는 불필요한 전체 연구 검색을 하지 않는다. 같은 세션에서 이미 읽은 자료는 변경 가능성이 없으면 다시 읽지 않는다.

## 자료와 작성 단계 확인

1. 요청이 발명신고서 작성, 기존 신고서 보완, 명세서 확장, 청구항 검토, 도면 수정 중 어디에 해당하는지 구분하라. 기본은 **발명신고서**이며 요청 없이 법률 문서 전체로 확대하지 마라.
2. 첨부 원본과 현재 버전을 읽고 기관 양식의 제목·항목·순서를 보존하라. 파일명이나 대화 속 추측으로 실제 출원본 또는 출원 상태를 확정하지 마라.
3. 아이디어, 논문, 발표 자료, 코드, 실행 결과 각각의 출처와 시점을 기록하라. 이전에 작성한 문서는 초안의 근거이지 구현 검증의 대체물이 아니다.
4. 이미 확보한 사실을 재질문하지 마라. 핵심 작동 원리가 불명확한 부분만 최소한으로 질문하고, 나머지는 검토 표시를 남겨 작성하라. 연구자 인적 사항·기여도·과제 정보는 제공된 것만 사용하라.

## 작성 절차

### 1. 발명의 기술적 중심 도출

다음 문장을 실제 내용으로 채워 한 단락으로 정리하라.
“[대상·입력]에서 발생하는 [구체적 문제]를 해결하기 위해 [구성들의 연결 또는 처리 절차]를 적용하여 [출력]을 생성하고, 그 결과 [기술적 효과]를 얻는다.”

키워드 나열이나 서비스 장점만으로 대체하지 마라. 발명의 중심을 지탱하는 처리와 일반적인 입출력·저장 기능을 구분하라. 사용자가 범위를 확정했다면 이를 유지하고, 다른 문제를 해결하는 확장은 별도 후보로 분리하라.

### 2. 구성과 근거 정리

각 구성을 다음 두 축으로 독립적으로 분류하라.
- 역할: 핵심 구성 후보 / 선택적 구체화 / 변형예 / 이번 범위 밖.
- 사실 상태: 구현 확인 / 설계·구상 / 실험 확인 / 미확인.

구현되어 있다는 이유만으로 필수 구성으로 만들지 마라. 미구현이라는 이유만으로 설명 가능한 구상을 자동 삭제하지도 마라. 제거 시 해결하려는 문제가 그대로 해결되는지, 대체 수단이 가능한지, 효과에 기여하는지를 근거로 판단하라.

기존 문서가 있거나 구현과 대조할 때 [근거 검토](references/evidence-review.md)를 읽고 대응표를 작성하라. 필수 구성에서 제외하거나 선택화한 항목에는 변경 이유를 남겨라.

### 3. 신고서 본문 작성

[본문 양식과 문체](references/disclosure-writing.md)를 읽어 기관 양식에 맞춰 작성하라. 양식이 없으면 해당 참고자료의 기본 목차를 사용하라.

해결 수단을 입력 → 처리 대상 선정 → 핵심 판정·변환 → 결과 구성 → 출력 순으로 구체화하라. 각 단계에 입력, 수행 주체, 조건, 결과를 기재하되 분야에 맞게 조정하라. 숫자·식·예외 처리는 재현과 이해에 필요한 만큼 본문에 넣어라. 근거 없는 성능 수치·실행 결과·지원 범위를 만들지 마라.

### 4. 도면 구성

[도면 작성 원칙](references/figures.md)을 읽어 도면별 설명 목적을 정하라. 구성도, 처리 흐름도, 입력–결과 예시는 후보이며 고정 개수나 필수 세트가 아니다. 짧은 상자 문구와 핵심 분기로 구조를 전달하고 상세 조건은 본문과 연결하라.

### 5. 내부 검토와 전달

다음 항목을 대조하고 발견한 오류를 고친 뒤 전달하라.
- 문제마다 해결 수단이 있으며 효과의 원인이 설명되는가?
- 용어, 단위, 수식의 분모·전제, 관계 방향이 일치하는가?
- 구현 완료와 변형예, 정확한 계산과 근사 계산이 구별되는가?
- 그림의 분기·화살표·부호가 본문과 같고 예외 경로를 오해하게 하지 않는가?
- 선택 구성이나 실시예 수치가 모든 경우의 의무 조건으로 바뀌지 않았는가?
- 미확인 사항을 단정하지 않았는가?

수정본에는 변경점과 이유, 실제 확인 범위, 남은 결정만 간단히 보고하라. 검증되지 않은 등록 가능성이나 오류 없음의 보증을 하지 마라. 명확한 결함이 없으면 선택적 보강을 이유로 끝없이 개정하지 마라.

## 후속 명세서·청구범위 작업

명시적으로 요청받았을 때만 신고서의 기술 설명을 명세서와 청구항 후보로 확장하라. 기존 틀을 보존하고 청구항 구성–본문 근거–도면–기존 기재를 연결하라. 독립항에 구현의 모든 기능을 열거하지 말고 발명의 중심과 선행기술 대비 검토 필요점을 제시하라. 종속항에 옮겨도 기존 기재 근거 문제가 자동으로 해결된다고 보지 마라.

실제 출원본·날짜·예정 절차가 확인되지 않으면 가출원, 보정, 우선권, 신규사항 또는 기한을 단정하지 마라. 법률·제도 안내가 필요한 경우 해당 관할의 최신 공식 자료를 확인하라. 최종 권리 범위와 절차 판단은 담당 변리사의 검토 항목으로 구체적으로 전달하되 기술 초안 작업을 중단하는 이유로 사용하지 마라.

## 파일과 재사용 범위

DOCX·PDF의 제작·편집·렌더링에는 해당 문서 스킬을 함께 사용하라. HWP는 실제 읽기·편집 지원 범위를 확인하고 변환본을 원본처럼 표시하지 마라. 최종 파일을 저장하고 링크로 전달하라. 검토용 대응표·미확인 메모·버전 이력은 제출 본문과 분리하라.

이 스킬에는 방법론만 축적하라. 특정 발명의 기술 구성, 가구 유무 같은 개별 범위, 개인식별정보, 미공개 원문 또는 특정 저장소의 구현 상태를 다른 발명의 기본값으로 가져오지 마라. 현재 문서·코드를 새로 확인하라. 사용자 피드백에서 재사용 가능한 원칙을 반영할 때에는 skill-creator의 저장 절차를 따르라.
