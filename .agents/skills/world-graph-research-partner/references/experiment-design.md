# 시스템·실험 설계와 결과 검토

아래는 설계·검토 기준이다. metric, baseline, 실험 설정의 예시를 이미 채택된 사용자 결정으로 쓰지 마라. 현재 주장에 필요한 비교를 선택하고 규모를 임의로 늘리지 마라.

## 연구 발전에 따른 전체 파이프라인 설계·자동화

연구 목표가 구체화되면 아래 항목 중 그 목표에 필요한 것을 함께 설계·구현·평가·보완하라. 후속 방법이나 시스템이 현재 모듈 구성을 그대로 유지해야 한다고 가정하지 마라.

- **자동화 범위:** 시작 입력과 최종 출력을 정의하고, 사전 지도 구축·학습·평가용 정답 준비와 실제 추론 과정을 구분하라. 어느 과정에 사람의 입력·보정·선택이 필요한지 명시하라. 추론 자동화를 평가할 때 평가용 수작업 라벨의 존재 자체를 자동화 실패로 취급하지 마라.
- **시스템 설계:** 각 단계의 역할, 데이터 형식, 필요한 정보, 의존성, 정상·실패 출력을 맞춰라. 사용자가 채택한 범위 안에서 데이터 입력부터 그래프 생성·매칭·결과 제공까지 연결 구조와 대안을 설계하라. 방법이 바뀌면 관련 단계와 인터페이스를 함께 수정하라.
- **구현과 통합:** 합의된 설계를 작은 구현 단위와 완료 조건으로 나누고, 요청 범위의 코드 작업을 수행하라. 실제 데이터를 흘려 보내며 중간 산출물과 최종 결과가 연결되는지 확인하라. 연구 기여와 무관한 인프라 구성을 필수로 추가하지 마라.
- **전체 과정 평가:** 주장에 맞춰 정확도뿐 아니라 전체 작업 성공률, 수동 개입, 실패·누락, 전체 지연, 처리량·자원 비용, 반복 실행의 일관성 등을 선택하라. 각 지표의 분모와 측정 범위를 정하고, 실패한 입력도 전체 평가에 포함하라. 자동화가 동작한다는 사실과 연구적 유효성을 각각 뒷받침하라.
- **진단과 보완:** 단계별 품질과 전체 결과를 연결해 오류 전파·정보 손실·병목을 찾고, 영향이 큰 지점을 우선 보완하라. 특정 모듈 교체나 수동 단계 자동화의 효과는 가능한 한 같은 입력·후속 설정으로 비교하라. 모듈 성능 향상이 최종 성능 향상으로 이어지는지도 확인하라.
- **연구의 연속성:** 이전 Oracle·pilot에서 확인한 근거를 활용하고, 새로운 설계가 바꾼 가정과 검증 공백을 식별하라. 기존 결과가 더 이상 적용되지 않거나 새로운 위험이 드러난 경우에 해당 검증을 다시 수행하라. 필요한 후속 실험·문헌 조사·설계 변경을 다음 의사결정과 연결하라.

## 문제 정의와 정보 경계

- 질의 입력, 지도 구축에 사용한 정보, 추론 시 사용할 정보, 출력 단위, 후보 풀, 정답 정의를 먼저 맞춰라. known-map room retrieval과 새로운 건물로의 일반화를 구분하라.
- 질의와 후보를 연결하는 정답 Room ID·이름·파일 경로·객체 전역 ID가 matching에 들어가는지 확인하라. 정답 식별자는 평가 단계에 분리하라. 좌표나 층 사전정보는 실제 질의에서 제공되는 조건인지 밝혀라.
- GT 객체 대응을 제공하면 그것은 관측 라벨의 정확성보다 강한 조건이다. 대응을 주는 별도 진단 실험으로 표시하라. 후보 지도에 있는 객체를 이미지에서 자동으로 식별했다고 간주하지 마라.
- 매핑 완료된 건물의 지도 전체를 추론에 쓰는 것은 과제 정의상 허용될 수 있다. 이를 test label 누출과 혼동하지 말고 지도 접근·학습·하이퍼파라미터 선택의 경계를 명시하라.

## Experiment A: Oracle observation

검증 질문은 “정의된 범위의 정확한 관측이 주어졌을 때 이 지도 표현과 retrieval 방법이 후보를 얼마나 구분하는가?”로 잡아라.

- 사람이 이미지에서 볼 수 있는 객체·관계를 라벨링한 Oracle과, 지도에서 임의 추출한 부분 그래프를 구분하라. 임의 부분 그래프는 실제 한 시점에 동시에 보일 수 없는 단서를 포함할 수 있다.
- 이미지 밖의 전체 방 정보를 주는 실험은 complete-room diagnostic으로 따로 해석하라. 실제 관측 Oracle과 같은 성능 표에 섞지 마라.
- 객체가 보이지 않는다는 사실을 지도에 객체가 없다는 증거로 쓰지 마라. 가림·시야·잘림과 실제 부재를 구분하고 negative evidence를 사용하려면 가시성 모델의 가정을 밝혀라.
- 2D의 above/left-of와 3D 세계좌표 기준 관계, 접촉·부착·인접의 기준이 동일한지 확인하라. 보이지 않는 3D 관계를 2D annotation에 정답으로 자동 주입하지 마라.
- Oracle이 제거하는 것은 정의된 관측 오류이다. 지도 오류, 표현 손실, 관측의 모호성, matcher 한계는 남는다. 특정 matcher에서 관측 잡음을 제거했다고 실제 성능에 대한 일반적 상한이 증명되는 것은 아니다.

검토할 축은 객체·관계 단서의 양, 구조 요소와 가구의 조합, 반복 구조·희소 환경, 관측 가능한 희소 단서 등이다. 단서 예산을 바꿀 때 같은 질의·후보 조건과 샘플링 규칙을 유지하라. 좋은 단서만 정답을 보고 선택한 경우 별도의 Oracle selection 조건임을 밝혀라.

## 그래프와 공간 정보의 기여 분리

| 비교 목적 | 검토할 비교군 또는 제거 실험 | 통제·해석 |
| --- | --- | --- |
| 객체 의미만으로 충분한가 | label set overlap, 객체 개수를 보존한 histogram/bag-of-objects, 필요하면 빈도 가중 의미 매칭 | set 기반 비교는 중복 개수를 잃으므로 이것 하나만으로 그래프의 필요성을 판단하지 말 것. |
| 관계가 추가 정보를 주는가 | 같은 객체·개수·속성을 유지하고 관계 사용 여부만 바꾼 비교 | 모델 용량, 가중치 튜닝, 후보 풀 등 함께 바뀐 요소를 밝힐 것. |
| 구조 단서가 도움이 되는가 | 가구만, 문·창·벽 등 구조 단서만, 결합 | 단서 수와 희소성 차이로 설명 가능한지 확인할 것. |
| 공간 기하·신뢰도·희소성의 효과 | 실제 제안법에 포함된 요소별 제거 | 존재하지 않는 구성요소를 필수 ablation으로 만들지 말 것. |
| 실제 이미지 입력의 유용성 | 가용 데이터와 목적이 맞는 image retrieval 또는 cross-modal 방법 | 입력·지도 모달리티, 사전학습·추가 이미지 비용, split을 나란히 밝힐 것. |

비교군은 실제로 같은 후보 집합을 검색하도록 하고, 약한 설정을 의도적으로 골라 격차를 만들지 마라. 본 연구에서 실행한 재현과 다른 논문의 공개 수치를 구분하라.

## Matching Score Design

- 먼저 필요한 능력을 정하라: 부분 관측 대응, 중복 객체 처리, 관계 정합, 점수의 크기 편향 통제, 불확실성 반영 등. 그 다음 간단한 score와 대안을 비교하라.
- 각 항의 의미, 값 범위, 정규화, 큰 방·큰 그래프에 대한 편향, 객체 대응 방법, 빠진 단서 처리, 점수 동률 규칙을 설명하라.
- confidence와 evidence_score를 사용할 때 추출 방법과 실제 이용 가능성을 확인하라. VLM의 자기보고 confidence나 여러 가중치를 합한 점수를 보정된 확률로 간주하지 마라.
- 희소성 통계가 학습 데이터에서 오는지 사전에 사용 가능한 참조 지도에서 오는지 밝히고, test 성능을 보고 가중치·threshold를 선택하지 마라.
- 숫자를 제안할 때는 초기 탐색값인지 검증으로 정한 값인지 표시하라. 가중합, 구조 일치, 학습 기반 matching 중 하나를 사용자 결정 없이 최종 방법으로 고정하지 마라.
- matching evidence는 선택을 설명하는 단서이다. 관계 제거 등의 개입 없이 evidence 출력 자체로 인과적 기여가 입증되었다고 주장하지 마라.

## Experiment B: 실제 pipeline

- 같은 질의 장면과 후보 지도에 대해 Oracle 입력과 실제 예측 입력을 비교하는 구성을 우선 검토하라. 중간 산출물을 보존해 오류가 생긴 단계를 추적하라.
- 객체 누락·오인식, 관계 오류, 그래프 변환 실패, 지도 불일치, matching 실패를 구분하라. 인식 모델이 빈 결과를 내거나 실패한 질의를 최종 정확도 분모에서 조용히 빼지 마라.
- A와 B의 점수 차이는 파이프라인의 관측 오류 영향을 진단한다. 데이터·matcher 등도 바뀌었으면 그 차이를 perception error만의 영향으로 단정하지 마라.
- 합성 뷰만 사용했으면 실영상 성능을 주장하지 마라. 합성–실제 간 객체 라벨·관계·외형·가시성 차이를 따로 검토하라.

## 지표·분할·결과 보고

- Room 후보 순위 평가에는 Top-1 accuracy, Recall@k 또는 Top-k inclusion, MRR 등을 목적에 따라 선택하라. 단일 정답의 의미, k, 후보 수, 동률 처리, query 수와 Room 수를 함께 명시하라.
- 방마다 관측 수가 다르면 query 평균과 room별 평균의 차이를 살펴라. 한 방의 많은 유사 이미지가 전체 결과를 지배하는지 확인하라.
- 같은 방·trajectory·합성 시점의 유사 표본이 학습·검증·시험에 어떻게 분포하는지 기록하라. 주장하는 일반화 단위에 맞춰 room/building 분할을 설계하고, 모든 연구에 무조건 같은 분할을 강요하지 마라.
- 작은 pilot은 효과크기·실패 사례 중심으로 해석하라. 충분한 표본으로 불확실성을 산정할 때는 반복 query를 독립적인 새 방으로 세지 말고 room/building 등 상관 구조와 같은 query의 paired 비교를 고려하라.
- retrieval 시간과 전체 지연을 구분하라. 실시간을 주장하면 perception·graph construction·matching·입출력 범위, 하드웨어, 지도 규모와 p50/p95 등 적절한 지연 근거를 확인하라. 임의의 보편적 실시간 기준을 만들지 마라.
- 알려진 후보 안에서 정답을 고르는 closed-set 결과로 unknown-room 거부 성능을 주장하지 마라. 해당 주장이 필요할 때만 unknown 입력과 거부 threshold 평가를 추가하라.

실험 제안은 검증할 주장, 사용 데이터와 조건, 비교군·통제 변수, 관측할 결과, 해석의 한계, 다음 결정을 가능하게 하는 완료 조건이 이해되도록 작성하라. 최소 pilot의 방·query 수가 필요하면 초기 제안으로 표시하고 데이터 확인 뒤 조정하라.
